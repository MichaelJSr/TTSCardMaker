- Publish (edit.js:422 `publish`, 56 `commitFiles`) = **git data API, one commit**, not contents API. `commitFiles(edits, message)`, edits = `{path: oldText => newText | null}`:
  1. `GET /repos/{repo}/git/ref/heads/{branch}` -> head sha
  2. `GET /repos/{repo}/git/commits/{head}` -> base tree sha
  3. for each path: `readFile(path, head)` = `GET /repos/{repo}/contents/{path}?ref={head}` with `Accept: application/vnd.github.raw+json` (returns raw text; 404 -> null). Calls `edit(old)`; skipped if result null or unchanged. No file sha needed.
  4. `POST /git/trees {base_tree, tree:[{path, mode:"100644", type:"blob", content}]}` (inline content, no separate blob call)
  5. `POST /git/commits {message, tree, parents:[head]}`
  6. `PATCH /git/refs/heads/{branch} {sha}` (no force). On 422 (not fast-forward = someone pushed) it loops from step 1 re-reading the files and re-applying the edit functions; up to 3 retries (`attempt >= 3` throws). Returns new commit sha, or null if nothing changed.
  Retry re-applies the pure transform to fresh content, which is exactly the "merge with concurrent bot updates" pattern needed. Repo/branch come from `S.data.repo` / `S.data.branch` ("MichaelJSr/TTSCardMaker", "main"). Rate: authenticated; each attempt = 3 + N reads + 3 writes.
  Commit message: `message || (what.length > 3 ? "Website edits: N changes" : "Website edit: A, B, C")` where what = card/page names (+ "people", "admins"). User may type a custom message.
  After commit: stores sent-ops, clears stage, `save()`, dialog "Published" with commit link `https://github.com/{repo}/commit/{sha}`; site rebuild takes minutes (workflow); bot reads on /update_stats.
- Files written (paths from `files()` edit.js:32 = defaults overridden by `S.data.files`): `MDW/Card Edits.json` (`editsFile`: JSON `{about, cards:{key:{fields..., _by, _at}}}`, keys sorted, fixed field ORDER, hand-formatted one-line-per-card), `MDW/Card Authors.txt` (`authorsFile`: INI-ish `[people]`/`[cards]` with `# --- credited to X (n) ---` groups), `MDW/Constructed Ban List.txt` (`banFile`: `Group:` headings, `Name - reason` lines), `MDW/Website Admins.txt` (admins, `#` comment lines preserved). - dist/ is NOT a copy of the repo. build_site.py (864 lines) writes only: data/*.json (4), assets/ (from site/assets), thumbs/, icons/, c/<id>/index.html (773), d/index.html, index.html, 404.html, og.jpg. workflow site.yml does a sparse checkout of just `/site/ /Types/ MDW/Fonts/stoogedings-src/stoogedings.json MDW/Constructed Ban List.txt MDW/Card Authors.txt MDW/Card Edits.json MDW/Website Admins.txt`; TTS/ is not checked out, and TTS/ is currently untracked locally (`git status`: `?? Bundling would need: add `/TTS/` to sparse-checkout and a `shutil.copyfile` into dist/data/ in build_site.py; and then the file would only update on a Pages rebuild (push to main + every 6 h cron + manual), i.e. stale vs. bot updates. Also the site workflow runs on every push to main, so every TTS save commit from the bot would trigger a ~site rebuild (with `concurrency: pages`, cancel-in-progress false) unless `paths-ignore: TTS/**` is added to the `push` trigger.
- Recommended for an editing view: fetch the save straight from GitHub at runtime, no bundling. Options:
  * `https://raw.githubusercontent.com/MichaelJSr/TTSCardMaker/main/TTS/Impossibility%20Simulator.json` (space must be %20, `urlPath()` app.js:~41 does it). raw.githubusercontent sends `Access-Control-Allow-Origin: *`, so `fetch()` works cross-origin (the site already loads PNGs from it for TTS FaceURLs and for `<img>`; image fetch for canvas uses crossOrigin anonymous, app.js:625). Use `fetch(url, {cache:"no-store"})`/cache-busting query to bypass browser cache (CDN still applies).
  * jsDelivr `https://cdn.jsdelivr.net/gh/MichaelJSr/TTSCardMaker@main/TTS/...` already used as fallback for old image versions (app.js:377-379); caches branch refs for ~12 h unless purged; jsDelivr refuses files > 20 MB (5.5 MB OK) but is a poor choice for "latest".
  * GitHub API contents with `Accept: application/vnd.github.raw+json` (what `readFile` does): up to 100 MB, always fresh, but needs token (60 req/h unauthenticated) and the editor's `readFile` only works signed in. This is the right call right before computing a publish (guarantees merge against latest).
- Large data handling already in code: lazy-loading of the big optional JSONs (history/versions/rules) via memoised promises; first screen only needs 409 KB cards.json; `content-visibility:auto` on tiles; `loading="lazy"`; thumbs at 240/360/720. No streaming/worker use; JSON.parse of 5.5 MB on main thread takes ~30-60 ms, fine; JSON.stringify for commit similar. Inline tree `content` for 5.5 MB works (tree API accepts up to 100 MB), but request body is a JSON-escaped copy (~6-7 MB) and the PATCH-retry loop re-uploads it each attempt.

## 6. Risks / gotchas for a Table tab
1. Bot conflict: the save changes on the bot machine; `commitFiles` retry only re-runs the transform on fresh text on 422. The ops must be written as id-based/idempotent operations against the freshly fetched JSON (GUID of object, not array index), and must fail loudly (per-op "target no longer exists / already moved") rather than silently skipping; show the user a summary of applied/skipped ops before commit. Pretty-printing/key order: write back with the same formatting as the bot (check indent and number formatting like `1e-05`, trailing newline, float precision); JSON.parse/stringify can round-trip floats differently (e.g. 1.0 -> 1, -0, 1e-7) and large diffs would appear in git; consider a reviewing diff stat or a text-level patch. Also TTS keeps `CardID`/`CustomDeck` keys in sync: moving/copying a card between decks requires adding its `CustomDeck` entry (FaceURL/BackURL) to the destination deck object and updating `DeckIDs`, and pruning unused ones; removing the last card of a Deck leaves an invalid 0/1-card Deck (TTS turns a 1-card deck into a Card object); deck "Transform" and `ContainedObjects` ordering (top of deck = last? verify) must be respected; GUIDs for copied cards must be regenerated (6 hex chars like `guid()` deck.js:152) and unique per save.
2. The editor's `token`, `commitFiles`, `readFile` are private closures, `stage` is card-op specific, and the editor's `publish` drops all of `stage` afterwards. Don't mix table ops into `stage.cards` (preview/applyOp/describe assume card fields; `find(op.id)` would fail). Add a separate stage key and export `commit`/`readFile`/`me` from `createEditor`; also decide whether the table stage joins the single "Review and publish" batch/bar (one commit touching both Card Edits.json and the save) or is independent.
3. Auth timing: `editor.init()` signs in asynchronously (edit.js:552); `editor.me` is null at first render. Render read-only first, then rerender on sign-in (app already calls `app.rerender()` after init sign-in). Token has `public_repo` scope and push is checked once; admin-only features use `me.admin`.
4. Routing: `route()` expects hash routes; nested args are joined `parts.slice(1).join("/")`. `renderView` runs again on `setParams` (replaceState) so view renders must be idempotent and cheap; async fetch results must check `parseHash().name === "table"` before painting (pattern at app.js:428). `rerender()` is invoked by editor after any edit, so the Table view must keep its own state outside the DOM (innerHTML is wiped on each render, losing scroll, form focus, drag state).
5. Mapping: save cards -> site cards (nicknames can differ from site names, duplicates share a PSD/art with different names, aliases, hidden cards are absent from `S.cards` but present in `S.byId`/`S.all`; custom FaceURL could point at old image versions). Fall back to showing the raw Nickname + FaceURL image when no site card matches. Bags (`Name: "Bag"` / `Custom_Model_Bag` etc.) and nested `ContainedObjects` are recursive; the site has no existing tree view.
6. Performance: a 5.5 MB save has thousands of objects; build the object tree lazily (collapsed bags/decks, `loading="lazy"` images, reuse `content-visibility:auto`) and use thumbs by `c.img` (240/360 webp) rather than the full PNG FaceURL (hundreds of KB each).
7. Staleness/caching: raw.githubusercontent CDN lag (up to 5 min) means a view that shows "latest" may be older than what publish will merge against; display the commit sha/time of what was loaded, and re-read via API before publish (already what `commitFiles` does).
8. Deployment: new asset needs no build change, but new generated routes/paths do; every push to main (incl. bot commits of the save) triggers the whole site workflow, and the 45-minute build; consider `paths-ignore`. The workflow sparse checkout excludes TTS/ so build-time reads of the save would need it added.
9. Security/HTML: all strings (Nickname/Description from the save) must be `esc()`-escaped; Description can carry TTS BBCode (`[b]`, `[ffffff]`), not HTML. Don't render untrusted FaceURLs without `esc` (same-origin img only).
10. Mobile/theme: follow the 980/860 px breakpoints and CSS variables; no drag/drop precedent, so use click-to-select + "Move to..." menus (keyboard accessible) first.
11. Concurrency between editors: ops staged locally against an old copy; on publish, re-validate ops against the fresh JSON and show conflicts before commit (the edit.js retry loop is silent about semantic conflicts).

## 12. Published decks (2026-10-21)
- Files: `site/decks/<owner>/<slug>.json` (format: `site/decks/README.md`; the folder holds only that README until someone publishes). One file per published hand; `<owner>` is the publisher's login (the folder must match the file's `owner` without case), `<slug>` comes from the name (`slugOf`: lowercase, non-alphanumerics to `-`, collapsed, trimmed, `hand` when empty, `-2`/`-3` on a clash when the publish dialog's Keep both is chosen; the default replaces) and matches `^[a-z0-9][a-z0-9-]{0,59}$`. Public: `{v: 1, owner, name (1-80, one line), description (≤ 500), cards (0-40 ids), field|null, updated}`. Private: `{v: 1, owner, private: true, kdf: {name: PBKDF2, hash: SHA-256, iter: 300000, salt (16 bytes b64)}, iv (12 bytes b64), data (AES-GCM-256 b64), updated}`; the plaintext is the UTF-8 JSON `{name, description, cards, field}` (the name too), the AES-GCM additionalData is `deck:<owner>/<slug>` with the owner lowercase, so a file moved under another path does not open. 16 KB per file.
- Module `assets/decks.js` (DOM-free at import, imports nothing from app.js): `slugOf`, validation with the build's limits, `fileOf(...)` the public file object, `encrypt(subtle, passphrase, owner, slug, payload)` / `decrypt(...)` (PBKDF2 → AES-GCM through `crypto.subtle`, so https or localhost only), base64 helpers, `deckTileHtml`/`tilesHtml`, `deckPageHtml`, `browserHtml` and the filter/sort helpers on plain data; everything through `esc`.
- Routes (app.js): `#/decks` the browser (tab highlight `deck`; no new tab, keys 1-6 unchanged), `#/decks/<owner>/<slug>` one deck; the Deck builder page gets "Published decks (N) · Browse" (N = the public count from cards.json, no fetch) and a Publish… button per saved hand (Sign in to publish when signed out). `data/decks.json` loads lazily like users.json. Share links of hands stay `d/#/deck/<code>`. A public deck's share page (`decks/<owner>/<slug>/`, no hash) is parsed by `parseHash` on a cold load; `syncUrl` keeps that URL until decks.json is loaded (a decks route is never collapsed to the root) and `decksReady` re-enters through `renderView`, so the title follows.
